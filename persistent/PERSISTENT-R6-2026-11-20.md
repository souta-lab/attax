## 2. 本ラウンドの変種設計

方式は本人の指示どおり最適化先行: ループ内は
drill＋ABAB のみ、フルゲートは採用判断点で一括。
ゲート再ロール禁止。

### 分離プローブ（bench 専用、出力は構成上無効/不変）

- **r6bpdbl**: kick 構築の倍加（M2 へ再計算し sink へ
  畳む。出力不変）→ 構築の清い直接費。
- **r6bpexp**: 展開（BFS の cand の kick 項）のみ除去
  → 展開＋その到達影の上限。r5bpm（910）− r5bpkey
  （≤432）− r5bpspin（≤140）− 構築（r6bpdbl）と
  合わせて kick 系の内訳を挟む。

### 実変種（ビット同一候補、drill で screening）

- **r6ba1**: 案A 移植。(i) 構築の項ごとの
  `if (c 範囲)` を clamp＋値マスク化（fetch は常に
  発行）、(ii) wallR の出所を sWallPk から
  subgroupBallot(wall) へ（atomicOr とゼロ化と
  LDS 読みを除去）、(iii) seed walk の rk を
  popc64 から running counter（Fpre + cnt − 1 − cIdx）
  へ。等価性: マスク化は元の分岐が返す値と同一、
  ballot は sWallPk のビットそのもの、counter は
  popcount の定義そのもの。
- **r6bk1**: 機構再設計の本体 — **active-kick 圧縮**。
  構築直後に `actK`（srcOf(k) ≥ 0 かつ M[k] ≠ 0 の
  k のビットマスク）を1回だけ作り、3つの消費側
  （BFS 展開・key 最小化・spin 証拠）が 15 スロット
  全走査をやめて actK の set bit だけを回す。
  ビット同一の根拠: 落ちる項は元の走査でも
  sk<0 で skip されるか M[k]=0 で寄与 0 の項のみ。
  spin については M[k]≠0 ⇒ k%5 < NK[k/5]（構築は
  i<NK の内側でしか M を書かない）ので、元の
  NK ガードと等価になる。
- **r6bh1**: hash パッキングの gather 削減 —
  **8 行ブロック転置**。rp のビット配置は
  「stream bit (10·r2 + j) = col[j] の bit
  (len−1−r2)」。行を 8 本ずつのブロックに分け、
  列ごとに 8 bit チャンクを取り、8×8 ビット行列
  転置（マスク交換3段、生成器内で全64位置を
  検証）で行マスク列に変換して詰める。row_mask10
  の 40 回 × 10 gather（≈2,000 命令/子）を
  ≈475 命令/子へ。生成器内で乱数盤面・len 1..45
  に対して旧形と完全一致を検証してから出す。

### 判定材料（着地判断は本体側）

- **r6bh1 は採用候補として強い**: ビット同一、
  両ペア同符号で −130.1。R5 の hash パッキング直接費
  ≈300 のうち gather 分 ≈130 を回収した形。資源不変。
- **r6ba1 は永続形ではほぼ中立**: −5.4（同符号だが
  誤差級）。§1 の予測どおり、永続形の構築部は HP3
  手展開形で wall も walk も既に counter 形のため、
  varB1 の −11% は来なかった。害はないが単独利得は
  ほぼ無い。
- **r6bk1 は不採用**: ビット同一だが +882.6 の大幅
  悪化（両ペア同符号・rep も密で確定）。VGPR 96→128
  が実測事実。[仮説] 固定15スロット走査は一様で
  コンパイラ展開と ILP が効く一方、set-bit while
  ループはレーン毎に発散・直列化し、actK が密な局面
  では節約自体も小さい。**active-kick 圧縮の方向は
  この測定で閉じる。**
- **r6bstk も不採用**: bk1 の悪化をそのまま継承
  （+859.8）。ba1 の −5 は相殺に遠く及ばない。
- **kick 系の内訳が挟めた**: 構築の清い直接費
  ≈+285（ペアa、rep 密。ペアb は +438.6 だが
  混合窓ノイズ込み）、展開 kick 項＋到達影の上限
  ≈240–280。R5 の系上限 ≈910（r5bpm）に対し
  構築 ≈285 + 展開 ≈260 + key ≤432・spin ≤140
  （相互に重なりあり）で整合。次に攻める清い対象は
  **構築そのもの**（計画テーブル化 = 案B の領分）。
- 採用候補の単純加算 [見積]: tk1（−121 実測）+

- G 天井の申し送り（R6-A、lanechat #38）: 本測定は

  影響を受けない。G>60 で着地する場合は gen_r6g1.py

## 6. r6g1 採用判定（2026-11-20、本体側）

- 根拠（正しさ）: フルゲート @72（GCEIL §6）と @84

  レジスタ・LDS 費用はゼロ。nwg ≤ 64 ではエントリ→

  @48 の bench も tk1 と同値（≈4,260 vs ≈4,259）で、

  ため 72 を採る。

  202/253 標本の混合窓。Δ は同一窓インターリーブの
  相対比較として実測だが、絶対値（≈3,870 そのもの）の

- 旧確定形の扱い: pfl_r4e2 = 4,600.7 µs/判断（G=48、
  クリーン窓、フルゲート合格）は履歴として残す。
  新土台 r6g1 @72 の ≈3,870 は混合窓の相対測定系の
  値であり、測定条件が違うので 4,600.7 と単純比較

- R5 読みの訂正（要約）: R5 の drill 由来の G
  レバー読み（span 2,447–2,976 µs）は、fan-in 天井で
  選択段が全 ply スキップされていた分の汚染だった

  @72 で −9.2% の中程度で、主戦場は stageS1/BP 側
  という R5 の結論は不変。詳細は GCEIL §1・§7。
- 申し送り: (1) tk1 系譜の変種を G>60 で使う場合は
  fan-in ハンクの移植が必須（§3 の申し送りと同一）。
  (2) 統合スタック（pfl_r6int1 系、§4）はハングの
  局所化・解消後に、土台を r6g1 へ差し替えて再生成
  するのが筋、というのが本体側の見通し。(3) G=96 の

### 機構分析: なぜ §4 の 7 分はハングではあり得ないか

ホスト（pfload.c / pfload_gd.c、検証経路は同一）の原典:

- 決定ごとに提出後 ctrl[0]（完了）/ ctrl[1]（エラー）を poll し、
  **期限は 20 秒**。1 決定に固まれば 20 秒時点で
  `dec N: host poll timeout` が印字され fault=2 になる。
  §4 の run は 7 分間ゼロ出力だったため、**どの決定も poll 期限に
  触れていない**。当時の進行レート（≈4.4–4.6 秒/決定）では
  7 分 ≈ dec 92 前後であり、「負荷下で遅いゲートを途中で止めた」
  が実態と整合する。CPU ≈93%・GPU busy ≈20% の署名は
  ホスト検証律速の進行形そのもの（GCEIL §5 が同一署名で
  確定済みの読み）。
- カーネル側の本物の desync も沈黙にはならない: gbar の spin
  （g_spin = 200,000 poll）と judgeTauStage の JP_DONE spin は
  上限到達で ctrl[30]（abort）と ctrl[1]（error）を立てて
  main を抜ける設計で、ホスト poll は ctrl[1] を見て fault=1
  として検証出力へ進む。つまり真のバリア desync は
  「fault=1 の出力」として現れ、「無出力の空転」にはならない。
- 静的な非終了監査（補強）: gbar の呼び出し列はデータ非依存
  （main の bk 列＋ emitOrderPX の 2 回、inout で整合）。
  シェーダ内のループは全て有界 — dedupeA の probe は
  16,384 回まで、BFS は V の単調増加で ≤64 レベル、set-bit
  walk は popcount まで、ticket ループは全域カウンタで終了。
  bt1 の sortStage は (k, j) ネットワークの回数が固定で、
  ba1 の追加 subgroupBallot は既存 ballot（占有列の構築）と
  同じ収束領域にある。3 成分のいずれにも、決定依存で
  終了しなくなる機構は見当たらなかった（PASS と整合）。

### 判定（着地判断は本体側）

- **pfl_r6int1 はフルゲート合格・正典 fnv 一致により、
  検証済みの統合形になった。** §4 の ABAB −278.1 µs/判断

  受け入れ 3,268 まで残り ≈1,055 [見積]）。
- §4 の「正典 fnv は得られていない。pfl_r6int1 はこの時点で
  着地不可」は、本節の合格により supersede される。当時の
  正しい評決は「評決なし（進行中のゲートを停止）」だった。
- G>60 で着地する場合は §3 の申し送りどおり gen_r6g1 の

## 8. ラウンド7: 構築の項作業そのものの削減（pfl_r7c1）

担当: レーン attax-r7cons（2026-11-20 17:34–17:52 JST）。土台 = pfl_r6int2（§7、フルゲート合格済み）@G=72。方式は最適化先行（drill＋同一窓 ABAB のみ、フルゲートは採用点バッチ、本節の変種は着地しない）。

### 8.0 まとめ

**pfl_r7c1: drill @72 合格、リソースは int2 と完全同一（SGPR 108 / VGPR 120 / SpillVGPR 0）で、同一窓 ABAB Δ = −61 µs/判断（−1.5%、両ペア同符号）。** 構築の項の重複分は取り切った。残差の主体は distinct な項集合そのもの（7–8 値/f）と k ごとの組立であり、重複起因ではない。VGPR コストゼロのため、採用点では int2 の上にそのまま積める。

### 8.1 設計: 項の値は (c, ky_j) だけで決まる

HP3 形の項 (i,j) は `t_j = F(c, ky_j)`、`c = xi + kx_j − kx_i`。つまり項の値は (i,j) そのものではなく **(cOff = kx_j − kx_i, ky_j)** で決まる。実テーブル（KX/KY/KN、VM 転記と PC `~/pfload/tables.glsl` の当該3行が sha256 一致 `79b1931f…` で検証済み）で数えると:

- nk=5 の kb（20種）: 項 15 個に対し distinct (cOff, ky) は **7–8 個**、distinct な fit ロードは **3–5 回**。
- 全項の **67%（208/312）が ky=0**（シフトなし・充填なし）。
- 全 kb で kx_0 = ky_0 = 0。

変種 **pfl_r7c1** は構築ループを f リテラル展開＋kb 専用ケース（switch、f ごとに到達可能な 8 kb）に置き換え、各 distinct 項値を1回だけ計算し、ky をコンパイル時定数として shlS を畳む（ky=0 は恒等、ky>0 は単一シフト＋充填、ky<0 は単一シフト）。dyPk は kb ごとに定数のニブル置換に、srcPk/M 組立は定数インデックスに落ちる。計画表化（案B・閉）と能動キック圧縮（bk1・閉）には踏み込んでいない。

等価性は生成器 `pf/gen_r7cons.py` が原形（ループ形）と専用形を模擬し、全 (cls, rots==1, r, xi) × 端点＋ランダム fit/wall パターン **52,224 ケースで全出力（M, NK, g_srcPkA/B, g_dyPk）一致**を証明してから書き出す（土台 sha `f005f432…` ピン留め、領域アンカー検証付き）。

### 10.1 prefixP の walk 実態（原典確認）

原典: `pf/pfl_r7c1.comp`（sha `adc2d9a6…`）。prefixP（L2774）は基数 walk（閾値キー T と need の決定）＋ merged compaction（count scan＋write scan）の2部構成。呼び出しは WG0 のみ、1 ply あたり:

- REPS 側（prefixAndChunk、ev=false）: ラウンド毎に1回。ply 内では keys（REPSORD）・mn/mx（mmu、cacheStage が ply 頭で確定）は不変で、変わるのは b だけ（256 から倍増、min(b, nReps)）。b ≥ n になると恒等フィル経路（walk なし）。
- EV 側（ev=true）: judgeTauStage が nEval>96 のラウンドで1回（nEval と mmv はラウンド毎に増える）、sortStage が ply 末に1回。後者は stamp（n・b・mn・mx・EVGEN）一致でキャッシュヒットし walk＋compaction を丸ごと skip する（EVGEN は judgePreCount がラウンド毎に進めるが、最終ラウンドの judgeTauStage と sortStage の間では進まない）。REPS 側に stamp はない。

walk の中身（L2823–2872）: レベル p は p0（mn^mx の最上位相違バイト）から 7 まで。1レベル = ヒストグラム走査＋数字決定。各レベルの走査は3形態:

- 全件走査（narrow でも arm でもない）: 全 n 件のキーを読み、前方一致でフィルタして atomicAdd で数える。arm 中は一致した index を TABFP へ atomic append する（次レベルの候補表を作るための追加の全件走査）。
- narrow 走査: TABFP[0..p_cand) の候補だけを読み直す。arm が発動するのは「選択した数字のブロック p_snext ≤ 512 かつ n > 512」のときだけで、発動したレベルの次のレベルから narrow になる。つまり narrow の利益が出る前に、全件走査が最低2回（発動レベル＋arm レベル）かかる。
- pfxarm（§9.3）が条件を ≤4096 かつ <n/2 へ広げても −0.2% ノイズだった事実と合わせると、(a) 既に大抵の呼び出しで narrow が早期発動している、(b) arm レベルの全件走査が税として残っている、(c) 残りの費用は compaction 側、のいずれか（または複合）。

compaction（L2877–2955）: count scan と write scan の2回の全件走査（各 n 件のキー読み直し）。レーン毎に連続チャンク（K=ceil(n/64) 件）を担当し、subgroupInclusiveAdd で自チャンクの書込オフセットを得る。bestKey（T 未満の最大キー）の追跡も write scan 側。

規模感: drill corpus は 2,495 ply / 180 判断、ply あたり子は平均 ≈3,619・最大 6,890。n（nReps・nEval）は千件級が常態。LDS は現行 5,120 B（RADV stats）。TABFP は [0, 32768) の 32,768 語で、使うのは walk の arm/narrow だけ（他段は読まない）。キー読み総量/呼び出し ≈（全件レベル数＋2）× n 件が上限の目安。

### 10.2 設計

狙いは arm レベルの全件走査（税）を取り、narrow を無条件化すること。変種 **pfl_r9tag**（結果不変）:

- 第1レベル（p == p0）の全件走査で、数え上げと同時に全要素を `(digit << 24) | index` のタグ付きで TABFP 領域 A へ atomic append する。第1レベルでは全要素が前方一致する（全キーは [mn, mx] 内にあり、先行バイトは定義により共通）ため、候補集合は全件そのもの。
- 第2レベル以降は領域を ping-pong する: 現領域のエントリを読み、タグ（前レベルで選ばれた数字）と一致するものだけキーを読み直して数え上げ、次の数字でタグ付けして次領域へ append する。タグ不一致のエントリはキーを読まない。前方一致フィルタは「領域に居ること」自体が保証する（構成による等価性）。
- 発動条件: n > 512 かつ 2n ≤ 32,768（TABFP 容量）かつ残りレベル ≥ 2。それ以外は現行の arm/narrow 機構をそのまま使う（フォールバック経路として残す）。
- 等価性: 各レベルのヒストグラムは現行と同一の集合に対する同一の数え上げ。数字決定・p_prefix・p_rem・p_T・p_need は不変。compaction は無変更。出力はビット同一のはず（drill で検証）。
- 走査量の変化: キー読みは n + s1 + s2 + …（s_k = k レベル目の生存候補数）に減る。現行は 2n +（narrow 後は ≤512 級）＋（narrow が発動しない場合はレベル数 × n）。追加コストは append の atomic と TABFP の語読み（タグ不一致分も含め領域全件）。pfxarm が中立だった事実からは、append atomic は支配的でない見込み。
- リスク: (1) append 先が単一カウンタへの atomicAdd で、競合が支配的になる可能性。(2) キーが極端に密集し s_k が減らない場合、TABFP 読み分だけ現行より悪化する。(3) VGPR 増（タグ操作分）。120 超は測定前に破棄。

あわせて費用内訳のサイジングプローブ2本（結果無効・測定専用）:

## 11. ラウンド10: prefixP の compaction 攻撃

担当: レーン attax-r10-compact（2026-11-20 20:0x– JST）。土台 = pfl_r7c1@G=72（sha256 `adc2d9a6…` ピン留め、着手時に再確認済み。r6g1 fan-in ハンクは L3078 のマーカーで含有を確認）。対象は §10.5 候補1: **compaction ≈485 µs/判断**（compstub で直接測定、prefixP ≈1,012 の最大の単一項目）。方式は最適化先行（drill＋同一窓 ABAB のみ、フルゲートは採用点バッチ、本節の変種は着地しない）。

### 11.1 compaction の現行構造（原典確認、pfl_r7c1.comp L2887–2955）

- count scan: レーン毎に連続チャンク（K=ceil(n/64) 件）を担当し、全件のキーを `selKeyOf` で読み直して cntA（k>T）/cntB（k==T）を数える。subgroupInclusiveAdd で自チャンクの書込オフセットを得る。
- write scan: 同じチャンクのキーを**もう一度全件読み直し**、>T を順序どおり PREFIXB/PFXIDX へ、==T の先頭 need 件を totA の後へ書く。あわせて p_tauIdx（rB==need−1）/p_nextIdxA（rB==need）を捕捉し、k<T の bestKey/bestIdx（チャンク内の最初の最大キー）を追跡する。
- bestKey の cross-lane 削減: 各レーンが pool[256+lane]/pool[320+lane]/sOrderPk[lane] へ書き、barrier の後に **lane 0 が64反復の直列ループ**で最大キー（同点は最小 index）を拾う。発動は no-next のとき（cntB == need で ==T ブロックの直後に次要素がない場合）だけだが、pool 書込みと barrier は常時かかる。
- compaction 内の barrier は3本（totA 読み後、bestKey 書込み後、lane 0 ブロック後）。
- 規模: keysOff 配列（REPSORD/EVORD）は各 16,384 語 = **n ≤ 8,192** が容量上限。よって K ≤ 128。

### 11.2 設計

**変種 pfl_r10fus（キー走査の融合）**: キー読みを1回にする。

- 第1走査（現 count scan の位置）で、数え上げに加えて (a) 各要素の分類（k>T=2 / k==T=1 / k<T=0、2 bit/件）を packed 語に詰めて TABFP scratch へ書く、(b) bestKey/bestIdx の追跡をここへ移す（反復順は現 write scan と同一の昇順で、意味論は不変）。
- staging の置き場所: TABFP + 16384 から 512 語。根拠: walk の arm/narrow が使うのは TABFP[0, n)（n ≤ 8,192）で、compaction 時点では walk は終了し TABFP は死んでいる（次 ply の resetScratch で全域クリアされる scratch であり、walk 自体が既に S3 で同領域を dedupe テーブルの跡地として再利用している）。レイアウトはレーン私有（語 index = lane × 8 + (t >> 4)、K ≤ 128 → レーン当たり最大8語）で atomic 不要。第2走査は自レーンの語だけを読む。
- 第2走査（現 write scan の位置）はキーを読まず、分類だけを見て現行と同一の書込み・捕捉を行う。bestKey は第1走査のレジスタ値から現行どおり pool/sOrderPk へ書く（削減方式は本変種では変えない — 変更を1つに絞る）。
- 出力（PREFIXB/PFXIDX/STATS/p_tauIdx/p_nextIdxA）はビット同一のはず。drill@72 で検証する。

**変種 pfl_r10fr（r10fus ＋ bestKey 削減の並列化）**:

- pool/sOrderPk への bestKey 書込みと lane 0 の64反復ループを、`subgroupShuffleXor` のバタフライ全削減（offset 32..1）に置換する。結合規則は現行ループと同一の全順序: 実候補（idx != 0xFFFFFFFF）がセンチネルに勝ち、キー最大、同点は最小 index。全レーンが同じ結果を持つため lane 0 はレジスタから直接 STATS を書ける。
- barrier の位置と本数は不変（write scan で他レーンが書く p_nextIdxA/p_tauIdx の可視性に barrier が要るため、そのまま残す）。削減されるのは LDS 往復（3書込み＋最大64読み）と no-next 時の直列64反復。

リスク: (1) §10.5 の教訓 — キー再読は直前に読んだばかりで cache に残り安い可能性があり、その場合の融合の利益は分類・64 bit 比較・アドレス計算の削減分だけになる。(2) VGPR 増（分類 packing、shuffle の一時変数）。**120 超は測定前に破棄**（§10.0 の規律）。(3) staging が global 経由（LDS 増は占有率を削るため避けた）で、往復交通が利益を食う可能性。

#### 11-C.0 sortStage の現行構造（原典確認、pfl_r7c1.comp L3426–3554）

呼び出しは main L3640 の1箇所（WG0 のみ、ply あたり1回、ラウンドループの後・gbar X5 の前）。比較器 btPrecedes はキー降順（kh→kl）・同点は ord（= coff）昇順の全順序（coff は ply 内で一意）。

- **相G（gather）**: nEval>96 なら prefixP(EVORD, nEval, 96, ev=true) を呼ぶ（stamp キャッシュがあり、最終ラウンドの judgeTau 呼び出しが通常ヒットする。§10.1）。要素ごとに selKeyOf（EVORD 2語読み）＋ EVLIST 2語読み（ord=coff / fit=child）を LDS へ集める。nEval≤96 なら PFXIDX を介さず直接集める。残り [keep, 128) はキー0 / ord=0xFFFFFFFF / fit=0 で埋める。末尾に barrier #1。

#### 11-C.1 設計

**恒等式（設計の軸）**: judgeBuildPX2 は EVLIST[2s] = child = plyCB(ply) + coff、EVLIST[2s+1] = coff と書く（L3328–3329）。よって gather される全要素（両分岐とも）で **fit ≡ plyCB(ply) + ord** が成り立つ。payload の fit は ord から復元でき、ネットワークに載せる必要がない。

**サイジングプローブ2本（冪等・drill 合格が前提、Δ＝直接費）**:

- r10sdblG: gather ブロック（prefixP 呼び出しを除くループ部＋padding）を複製する。同じ LDS 位置へ同じ値を書き直すため冪等。Δ が相G の直接費（prefixP 本体は除く）。
- r10sdblW: ネットワーク後のブロック（LDS 書き戻し＋barrier＋SELB ループ＋barrier＋lane 0 ブロック＋barrier）を verbatim 複製する。同値書きで冪等。Δ が相W の直接費（barrier 込み）。

**変種 r10swb（書き戻しのレジスタ直行）**: ネットワーク終了後、各レーンのレジスタは要素 lane（A）と lane+64（B）を正確に保持している（wave32 の LDS 経路でも終了時点ではレジスタが正本）。LDS 書き戻し＋barrier #2＋LDS 読みループを消し、`lane<keep → SELB[lane]=bfA`、`lane+64<keep → SELB[lane+64]=bfB` と直接書く。barrier #3・#4 と lane 0 ブロックは不変。結果不変。

**変種 r10snp（payload を載せないネットワーク）**: 恒等式により fit を全相から落とす。gather は EVLIST の偶数語読みと sFitW 書きをやめる（要素あたりグローバル読み 4→3）。レジスタ保持は (kh, kl, ord) の3語/要素になり、1段の shuffle は 8→6 本。j==32 の LDS 経路もキーと ord だけを交換する。書き戻しは SELB[i] = plyCB(ply) + sOrderPk[i]（LDS 経由のまま）。VGPR が下がる見込みで、その場合は占有率変化を結果に明記する。

**変種 r10sall（wb＋np＋barrier 食事）**: 上記2つの合成に加え、barrier #3・#4 を除去する。根拠: SELB と ST_NSEL の消費者は gbar X5 の後ろにおり、順序は gbar が保証する（他段も同じ機構に依拠）。h_* は lane 0 が書いて lane 0 だけが読み、nReps==0 経路は barrier なしで同じことをしている。末尾は「レジスタから SELB 書き → lane 0 の STATS/h_* 書き → return」になる。

リスク: (1) bitonic の ≈125 は VGPR 混ざりの上限寄りで、np の実利は shuffle 削減分（段あたり2本×28段）＋レジスタ圧低下の合計として測る。(2) wave32 環境（gl_SubgroupSize<64）では j==32 経路の書き換えが効くため、両経路とも原典どおり書き換える。(3) barrier #3/#4 の除去は drill のビット同一で検証するが、drill corpus で顕在化しない競合の可能性は判定節に明記する。
